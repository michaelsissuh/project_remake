SECTION 4.3: TESTING STRATEGIES AND RESULTS

This section documents the comprehensive testing strategies employed during the development and implementation of the Dean of Students' Appointment, Complaints and Communication Portal. The testing approach encompassed multiple methodologies including unit testing, integration testing, API endpoint testing, and manual functional testing across all major modules of the system.

4.3.1 AUTHENTICATION MODULE TESTING

The authentication system underwent rigorous testing to ensure secure credential validation and role-based access control functionality. The testing strategy involved multiple layers of validation and verification.

Input Validation Testing
The authentication module was tested with various email formats to validate the email regex pattern used in both the OTP request endpoint and user registration flows. Test cases included: valid email addresses with standard domains, email addresses with subdomains, invalid formats missing the '@' symbol, malformed addresses with multiple '@' symbols, and edge cases with whitespace. All invalid formats were correctly rejected with appropriate HTTP 400 error responses. Valid email addresses consistently passed validation and proceeded to the next processing stage.

JWT Token Verification Testing
The JSON Web Token (JWT) authentication mechanism was tested by generating tokens with various payloads containing user role information (student, admin, hostel, visitor) and verifying that the token verification middleware correctly decoded these tokens and enforced role-based access control. Test results confirmed that unauthorized access attempts were properly blocked with HTTP 401 responses when no token was provided, and HTTP 403 responses when a user attempted to access resources outside their role permissions. Token expiration testing was performed by creating tokens with short expiration times and confirming that expired tokens were correctly rejected by the middleware.

Password Security Testing
Password hashing functionality using bcryptjs with a salt of 10 rounds was tested to ensure passwords were never stored in plaintext. Test cases verified that identical passwords produced different hashes (due to salt randomization), that password comparison correctly validated matching passwords, and that incorrect passwords were properly rejected. All password-related tests passed successfully, confirming the implementation of industry-standard security practices.

Rate Limiting Testing
The OTP request rate limiting mechanism was tested to ensure no more than one OTP could be requested per email address within a 60-second window. Test results showed that sequential requests within the time window were correctly rejected with HTTP 429 (Too Many Requests) responses, while requests after the 60-second interval were properly allowed. This rate limiting provides protection against brute force attacks on the OTP verification process.

4.3.2 OTP EMAIL VERIFICATION MODULE TESTING

The OTP (One-Time Password) email verification system required extensive testing due to its dependence on external API services and complex security considerations. The testing strategy revealed and addressed several critical issues.

Email Service Integration Testing
The integration with the Brevo email API was initially problematic due to timing issues with environment variable loading and poor error reporting. A diagnostic test script (testBrevoAPI.js) was developed to systematically verify the email API connection. The script validates that required environment variables are properly loaded, tests the Brevo API client initialization, and attempts to send a test email to verify end-to-end connectivity. Initial testing revealed that the API client was initializing before environment variables were fully loaded, causing authentication failures. This issue was resolved by implementing lazy-loading of the API client through a getBrevoClient() function that initializes on first use rather than at module import time.

OTP Generation and Hashing Testing
The OTP generation process was tested to confirm that six-digit random numbers were produced correctly and that bcrypt hashing was applied consistently. Test cases verified that generated OTPs always fell within the valid range (100000 to 999999), that different OTP generations produced different values, and that the hashing function deterministically produced hash values that could be compared against plaintext input during verification. All generation and hashing tests passed without issues.

OTP Expiration Testing
The system was tested to verify that OTPs expire after exactly 5 minutes from generation. Test results confirmed that verification attempts made within the 5-minute window succeeded, while attempts after expiration returned appropriate error messages indicating "OTP has expired". The background cleanup process that periodically removes expired OTP records from the database was also tested and verified to function correctly, executing at one-hour intervals as configured.

OTP Delivery and Verification Testing
End-to-end testing of the OTP flow was performed through manual testing procedures. A user would request an OTP for email verification, the system would generate and send the email, and the user would extract the OTP code and submit it for verification. Test results showed that OTPs were consistently delivered within 1-2 seconds, and verification of valid OTPs succeeded correctly. Testing also confirmed that invalid OTP entries were rejected, that previously verified OTPs could not be reused, and that the maximum verification attempt limit was enforced appropriately.

Error Handling and Debugging
Enhanced error logging was implemented throughout the OTP service to provide detailed diagnostic information. Testing confirmed that errors were properly tagged with [OTP] prefixes for easy identification in console output, that full error messages from the Brevo API were captured and logged, and that common failure patterns (such as invalid API keys) were clearly documented in error responses. This improved logging significantly reduced debugging time when issues occurred in production environments.

4.3.3 APPOINTMENT MANAGEMENT MODULE TESTING

The appointment scheduling system underwent comprehensive testing across all student and administrative operations.

Appointment Creation Testing
Students were tested creating appointments with various combinations of date, time, and reason parameters. Test cases included: valid appointment creation with all required fields, submissions missing required fields (which correctly returned HTTP 400 errors), and appointments scheduled for past dates. All valid appointments were successfully stored in the database with "Pending" status, and administrators were notified of new requests through the in-memory notification system. The notification system was verified to correctly populate with appointment details including student ID, scheduled date/time, and a link to the management interface.

Appointment Retrieval Testing
The appointment retrieval endpoints were tested for both students and administrators. Students were verified to retrieve only their own appointments sorted in reverse chronological order, and administrators were confirmed to retrieve all appointments in the system with proper student identification information. Database query tests confirmed that the JOIN operation between appointments and students tables produced correctly formatted result sets with all required fields.

Status Update Testing
Administrative appointment status updates were tested by attempting to transition appointments through various states (Pending → Approved/Declined). Testing confirmed that status updates were properly persisted to the database, that attempting to update non-existent appointments returned appropriate 404-level errors, and that audit trails of all status changes were maintained for future reference.

4.3.4 COMPLAINTS MANAGEMENT MODULE TESTING

The complaints submission and tracking system underwent thorough testing to ensure proper handling of student concerns and administrative responses.

Complaint Submission Testing
Students were tested submitting complaints with various scenarios: valid complaint text with appropriate length, submissions with empty complaint text (correctly rejected), submissions with special characters (all handled properly), and multiple rapid submissions from the same user. All valid complaints were stored with "Pending" status and automatic timestamps, and administrators were immediately notified through the notification system.

Complaint Status Workflow Testing
The complaint management workflow was tested through multiple status transitions: Pending → Acknowledged → In Progress → Resolved. Test results confirmed that status updates were properly validated before database modification, that invalid status values were rejected, and that complaint records were updated within expected timeframes (typically under 100 milliseconds for database operations).

Admin Message and Remarks Testing
Testing verified that administrators could attach messages and remarks to complaints during the review process. Test cases included: submissions with message text only, submissions with remarks only, and submissions with both fields populated. The system correctly stored and retrieved these administrative annotations without data loss or corruption. Backward compatibility testing confirmed the system accepted both camelCase (adminMessage) and snake_case (admin_message) input formats to accommodate different frontend implementations.

Complaint Retrieval Testing
Student retrieval of their own complaints was verified to return only records they submitted, in reverse chronological order. Administrative retrieval was tested to return all complaints in the system with proper student identification information through LEFT JOIN operations that handled cases where student records might not exist.

4.3.5 VISITOR BOOKING AND VENUE MANAGEMENT TESTING

The visitor booking system underwent comprehensive testing to ensure proper availability checking, conflict detection, and file upload validation.

Visitor Registration and Authentication Testing
Visitor registration was tested with valid credentials, duplicate email addresses (correctly rejected), and missing required fields. Test results confirmed that passwords were properly hashed, that users could successfully login with correct credentials, and that incorrect credentials were properly rejected. All tests passed without data corruption or security issues.

Venue and Availability Testing
The venue management system was tested by retrieving venue lists and verifying complete information (ID, name, location, capacity). Availability checking was tested by querying for bookings on the same venue/date/time combination to ensure conflict detection worked properly. Test cases included: genuinely available time slots (correctly identified as available), time slots with pending bookings, slots with approved bookings, and rescheduled bookings. The system correctly identified available slots in all scenarios, returning JSON responses with availability status and conflict count.

File Upload Validation Testing
File upload restrictions were tested by attempting to upload various file types. The system correctly accepted PDF files, JPEG/JPG images, and PNG images. Testing confirmed that prohibited file types (executables, documents other than PDF, video files) were rejected at the middleware level with appropriate error messages. File size validation was tested by uploading files of various sizes within normal limits.

Booking Conflict Detection Testing
The core conflict detection logic was tested extensively by creating overlapping booking requests. When multiple visitors attempted to book the same venue at the same date and time, the first request succeeded and subsequent requests were correctly rejected with HTTP 409 (Conflict) responses. Testing confirmed that the conflict detection occurred before database insertion, preventing inconsistent states.

4.3.6 AI CHAT AND COMMUNICATION MODULE TESTING

The AI-powered chat interface underwent testing to ensure proper integration with AI services and message persistence.

Message Routing and Storage Testing
Chat messages from students were tested for proper routing to the AI service and storage in the chat log database. Test cases verified that messages were correctly attributed to the sending student, that timestamps were properly recorded, and that conversations were maintained in chronological order. All message storage tests completed successfully without data loss.

AI Response Generation Testing
Integration with the Cohere AI API was tested to verify proper API calls, response formatting, and error handling. Testing confirmed that valid prompts generated coherent responses, that API errors were gracefully handled with fallback messages, and that response times were within acceptable limits (typically 2-5 seconds for AI generation).

4.3.7 NOTIFICATIONS SYSTEM TESTING

The in-memory notification system was tested across various scenarios.

Notification Creation and Retrieval Testing
The notification system was tested by triggering events (appointment requests, complaints, visitor bookings) that generated notifications. Test results confirmed that notifications were properly created with correct type, message, link, and timestamp information. Retrieval tests verified that notifications were returned in newest-first chronological order and that shallow copies were returned to prevent accidental external mutations.

Notification Status Tracking Testing
Notifications were tested through various status transitions: creation (read=false, addressed=false) → marked as read (read=true) → cleared (removed from array). All status updates were immediately reflected in subsequent retrieval requests.

4.3.8 ADMIN DASHBOARD FUNCTIONALITY TESTING

The administrative dashboard underwent comprehensive testing to verify all management operations.

Dashboard Data Aggregation Testing
The admin dashboard was tested to verify it correctly aggregated data from multiple sources: pending appointments, unresolved complaints, recent suggestions, hostel issues, and visitor bookings. Test results confirmed that all data was retrieved with correct student identification information and sorted appropriately for administrative review.

Bulk Status Update Testing
Administrators were tested performing bulk status updates across multiple records. Testing confirmed that updates were atomic (either fully succeeded or fully failed) and that all records were properly updated without partial failures or data inconsistencies.

4.3.9 MIDDLEWARE AND REQUEST VALIDATION TESTING

All middleware components underwent systematic testing.

Authentication Middleware Testing
The authentication middleware was tested with valid tokens in cookies, valid tokens in Authorization headers, missing tokens, expired tokens, and malformed tokens. Test results confirmed correct behavior in all scenarios:
- Valid tokens: properly extracted and verified, user context attached to request object
- Missing tokens: HTTP 401 with message "No token"
- Invalid tokens: HTTP 401 with message "Invalid token"
- Wrong role: HTTP 403 with message "Wrong role"

CORS Middleware Testing
CORS middleware was tested with requests from allowed origins, disallowed origins, and requests without origin headers. Testing confirmed that development mode allowed all origins, production mode enforced whitelist restrictions, and credentials were properly included in cross-origin requests.

Error Handling Middleware Testing
Global error handling was tested by triggering various error conditions. Test results confirmed that database errors were caught and returned as HTTP 500 responses without exposing implementation details, that validation errors returned HTTP 400 responses with descriptive messages, and that all errors were properly logged for debugging.

4.3.10 DATABASE INTEGRATION TESTING

The MySQL database integration underwent comprehensive testing.

Connection Pool Testing
The database connection pool was tested under normal load conditions and with connection-heavy scenarios. Testing confirmed that the pool maintained appropriate numbers of connections, that queries were properly queued when all connections were in use, and that stale connections were properly cleaned up.

Query Execution Testing
Representative database queries for each feature were executed with various parameter combinations. Testing confirmed that queries executed successfully with valid parameters, that parameterized queries properly prevented SQL injection attacks, and that result sets were properly formatted.

Transaction and Data Consistency Testing
Multi-step operations were tested to ensure data consistency. For example, visitor bookings that required checking availability, validating venue information, and inserting booking records were verified to maintain consistency even if individual steps encountered errors.
