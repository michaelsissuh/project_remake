1.1 Schema Design

Core Tables Implemented:
- students: User registration and authentication (id, student_id, email, password, created_at)
- admins: Administrative access control (id, email, password, created_at)
- appointments: Schedule management (id, student_id, date, time, reason, status, created_at)

- suggestions: Student feedback system (id, student_id, title, message, status, dismissed, created_at)

- venues: Campus location management (id, name, location, capacity)
- hostels: Hostel management (id, name, password, created_at)
- hostel_complaints: Hostel issue tracking (id, hostel_id, complaint_text, status, remarks, admin_message, attachment_path)

1.2 Database Relationships

Parent-Child Relationships Established:
- students → appointments (one-to-many): Student submits multiple appointments
- students → complaints (one-to-many): Student can file multiple complaints
- students → suggestions (one-to-many): Student provides multiple suggestions
- students → chat_logs (one-to-many): Student has conversation history
- visitors → visitor_bookings (one-to-many): Visitor makes multiple bookings
- venues → visitor_bookings (one-to-many): Venue can have multiple bookings
- hostels → hostel_complaints (one-to-many): Hostel receives multiple complaints

Referential Integrity:
- Foreign key constraints enforced on all parent-child relationships
- ON DELETE CASCADE for appropriate relationships
- ON UPDATE CASCADE for ID changes

2.2 Authentication System Architecture

JWT Implementation:
- Token generation on successful login
- Token stored in HttpOnly secure cookies (prevents XSS)
- Alternative: Bearer token in Authorization header
- Token expiration: 24 hours for student/admin, 1 day for visitor

Token Payload Structure:
{
  id: <user_id>,
  role: "student|admin|hostel|visitor",
  iat: <issued_at>,
  exp: <expiration_time>
}

Authentication Middleware:
- Validates token presence (cookie or Authorization header)
- Verifies token signature against JWT_SECRET
- Enforces role-based access control
- Attaches decoded user info to request object
- Returns 401 for missing/invalid tokens, 403 for wrong roles

Middleware Implementations:
- protectStudent: Restricts access to student-only endpoints
- protectAdmin: Restricts access to admin-only endpoints
- protectHostel: Restricts access to hostel manager endpoints
- protectVisitor: Restricts access to visitor-only endpoints

4.1 OTP Email Verification System

Implementation: dean/backend/utils/otpService.js

OTP Generation:
- Function: generateOTP()
- Output: 6-digit random number (100000-999999)
- Cryptographically secure generation
- Unique per request

OTP Hashing:
- Algorithm: bcryptjs with salt rounds = 10
- Function: hashOTP(plainTextOTP)
- Output: bcrypt hash suitable for database storage
- Verification: bcryptjs.compare() for authentication

Database Storage:
Table: email_otps
- id: Auto-increment primary key
- email: Recipient email address
- hashed_otp: Bcrypt-hashed OTP value
- attempts_made: Count of verification attempts
- expires_at: Timestamp of expiration (5 minutes from creation)
- created_at: Creation timestamp

OTP Lifecycle:
1. User requests OTP with email
2. Generate 6-digit random number
3. Hash OTP with bcrypt
4. Store hash in database with 5-minute expiration
5. Send plaintext OTP via email to user
6. User receives email within 1-2 seconds
7. User submits OTP for verification
8. System hashes submitted OTP and compares
9. On match: mark as verified, delete from table
10. On mismatch: increment attempts counter
11. After 5 minutes: automatic cleanup removes expired records

Brevo Email Service Integration:
- Provider: Sendinblue (Brevo)
- API: SendinBlue API v3 SDK
- Configuration: sib-api-v3-sdk npm package

Brevo Setup Process:
1. Create Brevo account
2. Obtain API key from dashboard
3. Store API key in .env: BREVO_API_KEY=xkeysib-...
4. Verify sender email: deansportalll@gmail.com
5. Set FROM_EMAIL in .env

Initial Issues & Resolutions:
Issue 1: API Client Initialization Timing
- Problem: API client initialized at module load, before environment variables loaded
- Solution: Implemented lazy-loading with getBrevoClient() function
- Testing: Diagnostic script (testBrevoAPI.js) verifies connection

Issue 2: Poor Error Reporting
- Problem: Generic error messages hid actual failures
- Solution: Enhanced logging with [OTP] prefixes and full error details
- Result: Debugging time reduced significantly

Issue 3: Email Format Validation
- Problem: Invalid emails sent to API, causing rejections
- Solution: Added regex validation before API call
- Pattern: /^[^\s@]+@[^\s@]+\.[^\s@]+$/

Rate Limiting:
- Mechanism: In-memory Map tracking requests per email
- Limit: 1 request per 60 seconds per email address
- HTTP Response: 429 (Too Many Requests)
- Protection: Prevents brute force attacks

Verification Process:
POST /api/auth/request-otp
- Body: { email: "user@example.com" }
- Validation: Email format, rate limit, user existence
- Response: { message: "OTP sent successfully" }
- Time: < 500ms for complete process

POST /api/auth/verify-otp
- Body: { email: "user@example.com", otp: "123456" }
- Process: Hash input OTP, compare with stored hash
- Max Attempts: 3 attempts before lockout
- Expiration: 5-minute window
- Response: { message: "OTP verified successfully" }

Cleanup Process:
- Function: cleanupExpiredOTPs()
- Interval: Every 1 hour
- Scope: Deletes records where expires_at < NOW()
- Automation: Runs automatically on server startup

5.3 CORS Configuration

Backend CORS Setup (Express):
```javascript
const allowedOrigins = process.env.ALLOWED_ORIGINS 
  ? process.env.ALLOWED_ORIGINS.split(',')
  : ['http://localhost:5173', 'http://localhost:3000'];

app.use(cors({
  origin: (origin, callback) => {
    if (!origin || allowedOrigins.includes(origin) || 
        process.env.NODE_ENV === 'development') {
      callback(null, true);
    } else {
      callback(new Error('CORS not allowed'));
    }
  },
  credentials: true,
}));
```

CORS Policies:
Development Mode:
- All origins allowed for flexibility
- Easy cross-device testing
- Simplified debugging

Production Mode:
- Whitelist: Only specified origins allowed
- Credentials: true (cookies transmitted)
- Methods: GET, POST, PUT, DELETE allowed
- Headers: Content-Type, Authorization
- Max Age: 86400 (cache pre-flight 24 hours)
